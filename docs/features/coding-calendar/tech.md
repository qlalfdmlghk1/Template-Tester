# coding-calendar — tech 기록

## [2026-07-27] Firestore 조회 호출 감소 (#67)

### 배경 — 무엇이 병목이었나

Firestore 무료(Spark) 플랜 한도는 저장 1 GiB / 읽기 50,000·쓰기 20,000·삭제 20,000 per day / 송신 10 GiB per month.

**저장 용량은 병목이 아니다.** `solveLogs` 문서 1건을 실제 필드 구성으로 계산하면 약 **468 bytes**(필드 291B + 문서명 145B + 오버헤드 32B). 172건이면 79 KB이고, 1 GiB에 닿으려면 약 **229만 건**이 필요하다. 사실상 무시해도 되는 축.

**실제 병목은 읽기 쿼터였다.** `useSolveLogs`가 페이지에 진입할 때마다 사용자 전체 기록을 조회하는 구조였다.

| 기록 수 | 진입 1회당 읽기 | 하루 가능 진입 횟수 |
| ------- | --------------- | ------------------- |
| 172건   | 172             | 290회               |
| 1,000건 | 1,000           | 50회                |
| 3,000건 | 3,000           | 16회                |

기록이 쌓일수록 급격히 조여온다. 여기에 `src/app/main.tsx`의 React `StrictMode` 때문에 **개발 모드에서는 effect가 두 번 실행**되어 진입당 344 읽기가 된다. HMR 저장마다 재실행되므로 실제로는 개발 중 소모가 가장 컸다.

### 적용한 대책 — 세션 캐시 (1단계)

`src/entities/solve-log/api/solveLogCache.ts` 신규.

- **메모리(모듈 스코프) + sessionStorage 2단 캐시** — 페이지 새로고침에도 살아남아 개발 중 재조회를 없앤다
- **TTL 30분** — 새 기록은 동기화·수동 입력으로만 생기고 그때 캐시를 갱신하므로 짧을 이유가 없다. 다른 기기에서 동기화한 경우를 위한 안전장치 성격
- **userId 불일치 시 캐시 무시** — 계정 전환 시 이전 사용자 데이터가 보이지 않게
- **`solvedAt` 복원** — JSON 왕복에서 `Date`가 문자열이 되므로 읽을 때 되살린다
- **폴백** — 저장 형식이 깨졌거나 sessionStorage를 못 쓰는 환경은 "캐시 없음"으로 처리
- **`dedupe()`** — 진행 중인 조회를 하나로 합쳐 StrictMode 이중 마운트에서도 요청이 한 번만 나간다

변경 반영 정책:

| 동작                      | 처리                                            |
| ------------------------- | ----------------------------------------------- |
| 수동 기록 추가·수정·삭제  | `patchCache`로 캐시 직접 갱신 (재조회 없음)     |
| 대량 동기화 (`saveSolveLogs`) | `clearCache` 후 `refresh`로 다시 읽기       |
| 로그아웃                  | `clearSolveLogCache()` (`features/auth/api/auth.api.ts`) |

로그아웃 시 비우는 것은 공용 PC에서 다음 사용자 세션에 이전 기록이 남지 않게 하기 위함이다.

**효과**

| 상황                | 이전     | 이후 |
| ------------------- | -------- | ---- |
| 30분 내 페이지 재진입 | 172 읽기 | 0    |
| 개발 중 새로고침    | 172 읽기 | 0    |
| StrictMode 이중 마운트 | 344 읽기 | 172  |

**검증** — `solveLogCache.spec.ts` 15 케이스: TTL 경계, 사용자 불일치, sessionStorage 왕복 및 `Date` 복원, 깨진 JSON 폴백, `patchCache`가 만료 시각을 연장하지 않을 것, `dedupe` 동시 호출·실패 후 복구.

### 설계 단계에서 함께 줄인 것

- **문제번호 매핑에 트리 1회 조회 사용** — 커밋 메시지에는 문제 번호가 없어 원래는 커밋마다 상세 API가 필요했다. 대신 `git/trees/HEAD?recursive=1`을 한 번 읽어 "제목 → 번호" 색인을 만든다. 그 결과 전체 백필 GitHub 요청이 **커밋 페이지 3회 + 트리 1회 = 4회**로 끝난다(비인증 한도 60회/시간). 커밋마다 상세를 불렀다면 수백 회였다.
- **증분 동기화** — `since` 파라미터 기반. 문서 ID가 결정적 키라 백필 구간과 증분 구간이 겹쳐도 중복 생성이 아니라 덮어쓰기가 된다.

### 남은 개선안 (2단계 — 기록 1,000건 근처에서 전환)

- **월 단위 조회**: `where dateKey >= 월초 <= 월말` + `userId`로 보이는 달만 읽으면, 진입당 읽기가 전체 기록 수와 무관하게 30건 내외로 고정된다.
- 단, **총 풀이 수·연속 학습일(streak)은 전체 데이터가 필요**하므로 동기화 시점에 계산해 `calendarSettings` 문서에 요약으로 저장해야 한다.
- **지금 도입하지 않은 이유**: 172건 규모에서는 아직 없는 문제를 미리 푸는 셈이고, 요약 캐시가 생기면 정합성을 맞춰야 할 지점이 하나 늘어난다.

### 쓰기 쪽 참고

- 전체 백필 = 172 쓰기. "전체 다시 읽기" 버튼은 매번 172건을 무조건 다시 쓴다(하루 116회까지 가능하나 불필요한 소모).
- 변경분만 쓰려면 기존 문서를 읽어 비교해야 해서 읽기가 더 드는 역효과가 난다. 증분 동기화(`since`)가 이미 그 역할을 한다.
